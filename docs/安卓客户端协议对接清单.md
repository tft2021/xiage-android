# 小智安卓客户端 · 协议对接清单

面向实现者的落地文档。所有内容均来自两份可交叉验证的来源：

- 固件源码 `78/xiaozhi-esp32`：`main/ota.cc`、`main/system_info.cc`、`docs/websocket.md`
- 参考客户端 `huangjunsen0406/py-xiaozhi`：`src/protocols/`、`src/activation/ota.py`、`src/audio_codecs/opus_codec.py`、`src/core/state_manager.py`

并已对官方线上服务做过实测验证（见 `probe/官方服务器接入验证报告.md`）。

## 一、总体四阶段

```
① 设备身份   生成并持久化 Device-Id / Client-Id
      ↓
② OTA 配置   拉取 websocket.url / token、mqtt 配置
      ↓
③ 激活绑定   显示 6 位码 → 用户去 xiaozhi.me 绑定 → 轮询 /activate
      ↓
④ 会话       WebSocket 握手 → hello → listen → Opus 上下行
```

## 二、常量表

来源：`py-xiaozhi/src/constants/constants.py`

| 常量 | 值 | 说明 |
|---|---|---|
| `INPUT_SAMPLE_RATE` | `16000` | 上行采样率，**协议固定值**，不可改 |
| `CHANNELS` | `1` | 单声道，**协议固定值** |
| `OUTPUT_SAMPLE_RATE` | `24000` | 下行采样率，服务端协商决定 |
| `FRAME_DURATION` | `20` / `40` / `60` | 帧时长（ms），三选一 |
| `INPUT_FRAME_SIZE` | `320` | 每帧样本数 = 16000 × 20 / 1000 |

枚举：

```kotlin
enum class DeviceState    { IDLE, LISTENING, SPEAKING }
enum class ListeningMode  { REALTIME, AUTO_STOP, MANUAL }   // 线上值 realtime / auto / manual
enum class AbortReason    { NONE, WAKE_WORD_DETECTED, USER_INTERRUPTION }
```

**注意 `ListeningMode` 的枚举名与线上取值不同**：`AUTO_STOP` 线上发 `auto`。写序列化时务必映射。

帧时长建议：

| 取值 | 延迟 | 适用 |
|---|---|---|
| 20 ms | 最低 | CPU 充裕的旗舰机，追求响应速度 |
| 60 ms | 较高 | 与 ESP32 固件默认一致，CPU 占用最低，兼容性最稳 |

**新项目建议先用 60 ms**（对齐固件 `OPUS_FRAME_DURATION_MS`），稳定后再试 20 ms。

## 三、设备身份

| 标识 | 固件来源 | 安卓实现 |
|---|---|---|
| `Device-Id` | Wi-Fi MAC 地址 | 首次启动生成伪 MAC（`AA:BB:CC:DD:EE:FF` 格式），存 SharedPreferences |
| `Client-Id` | NVS 中的 UUID | `UUID.randomUUID().toString()`，存 SharedPreferences |

两个值**必须在卸载前保持不变**，否则每次启动都是新设备、都要重新激活。

安卓拿不到真实 MAC（Android 6+ 已随机化），伪造即可 —— 实测服务端不校验 MAC 的 OUI。

## 四、OTA 配置拉取

### 请求

`POST https://api.tenclass.net/xiaozhi/ota/`

**请求头**（`py-xiaozhi` 实测可用的最小集）：

```
Device-Id         <device-id>
Client-Id         <client-id>
Content-Type      application/json
User-Agent        {BOARD_TYPE}/{APP_NAME}-{APP_VERSION}
Accept-Language   zh-CN
```

`Activation-Version` 头**不需要传**（缺省即 v1，即"无 eFuse 序列号"路径）。

### User-Agent 是硬性校验点

格式必须是 `{BOARD_TYPE}/{APP_NAME}-{APP_VERSION}`。实测：

| User-Agent | 结果 |
|---|---|
| `bread-compact-wifi/py-xiaozhi-2.1.1` | 200 |
| `my-android-phone/2.1.1` | 200 |
| `Xiaozhi/2.2.2 (esp32s3) IDF/v5.4.0` | **400 Invalid board type or app version** |

格式只要满足 `名字/版本` 即可，**板型名不做白名单校验**。实测伪装成真实板型 `bread-compact-wifi` 与随机板型结果完全一致（都进测试组），所以不必伪装，直接用自己的名字。

### 请求体

`py-xiaozhi` 用的精简载荷（推荐照抄，比 ESP32 固件那套短得多，且实测可用）：

```json
{
  "application": {
    "version": "1.0.0",
    "elf_sha256": "unknown"
  },
  "board": {
    "type": "xiaozhi-android",
    "name": "xiaozhi-android",
    "ip": "192.168.1.100",
    "mac": "AA:BB:CC:DD:EE:FF"
  }
}
```

### 响应

```json
{
  "server_time": {"timestamp": 1788185775581, "timezone_offset": 480},
  "firmware": {"version": "1.7.2", "url": ""},
  "mqtt": {
    "endpoint": "api.tenclass.net",
    "client_id": "GID_test@@@aa_bb_cc_dd_ee_30@@@2f43176d-...",
    "username": "eyJpcCI6IjExNy4xNTEuOTcuMTIwIiwiYyI6MH0=",
    "password": "Pjpg3SWja4Hw56wSRclfOHe1fKkZvJ/hK8jbj0HZnLs=",
    "publish_topic": "device-server",
    "subscribe_topic": "null"
  },
  "websocket": {
    "url": "wss://api.tenclass.net/xiaozhi/v1/",
    "token": "test-token"
  },
  "activation": {
    "code": "997945",
    "message": "xiaozhi.me\n997945",
    "challenge": "170af108-bd08-4bb7-b644-5b77ac9834a5"
  }
}
```

**解析要点**（`py-xiaozhi` 的 `_process_ota_response`）：

```kotlin
// 1. websocket 段：token 缺失或空都按 "test-token" 兜底
val token = ws["token"]?.takeIf { it.isNotBlank() } ?: "test-token"

// 2. 是否存在 activation 段，直接决定设备是否已激活
val needsActivation = response.containsKey("activation")
```

固件对 `websocket` 段的字段名不做硬编码，遍历所有键值对存起来 —— 安卓端同样建议**整体存 Map**，别写死 `token`，防止服务端改键名。

### 未绑定的三个特征（用于自检）

同时出现即表示设备**尚未绑定账号**，只能拿测试组凭据：

1. `mqtt.client_id` 前缀为 `GID_test`
2. `mqtt.subscribe_topic` 是字符串 `"null"`
3. `websocket.token` 等于 `"test-token"`

补充：`mqtt.username` 是 Base64，解码形如 `{"ip":"117.151.97.120","c":0}`，其中 `c` 疑似绑定标志（未绑定 `0`）。

## 五、激活绑定

### 端点

`POST https://api.tenclass.net/xiaozhi/ota/activate`

### 请求体

无 eFuse 序列号时固件直接发 `{}`：

```cpp
// main/ota.cc
std::string Ota::GetActivationPayload() {
    if (!has_serial_number_) {
        return "{}";
    }
    ...  // 有序列号才走 HMAC-SHA256
}
```

手机没有 eFuse 硬件密钥，**必须走这条路径**。请求头与 OTA 一致。

### 状态码语义

| 状态码 | 含义 | 客户端动作 |
|---|---|---|
| `200` | 激活成功（响应 `{"message":"Device activated","device_id":1763214}`） | 进入会话阶段 |
| `202` | 等待用户在网页输入激活码（`{"message":"Device activation timeout"}`） | 继续轮询 |
| 其他 | 失败 | 报错 |

### 轮询参数

`py-xiaozhi` 的值：`ACTIVATION_MAX_RETRIES = 60`，`ACTIVATION_RETRY_INTERVAL = 5`（秒）。
即最多轮询 5 分钟，每 5 秒一次。

### UI 流程

1. App 首次启动 → 调 OTA → 拿到 `activation.code`（6 位）
2. 界面显著位置显示这 6 位码 + 提示"请访问 xiaozhi.me 登录后输入"
3. 同时启动轮询 `/activate`
4. 收到 200 → 持久化激活状态 → 重新调 OTA 拿真实凭据 → 进入会话

**这等价于 ESP32 把 6 位码显示在 OLED 屏幕上**，只是换成了手机界面。

## 六、WebSocket 会话

### 握手

```
GET /xiaozhi/v1/ HTTP/1.1
Host: api.tenclass.net
Authorization: Bearer <token>
Protocol-Version: 1
Device-Id: <device-id>
Client-Id: <client-id>
```

连接参数（`py-xiaozhi` 实测值）：

| 参数 | 值 |
|---|---|
| `pingInterval` | 20 s |
| `pingTimeout` | 20 s |
| `openTimeout` | 5 s |
| `closeTimeout` | 10 s |
| `maxFrameSize` | 10 MB |
| `compression` | 关闭（`permessage-deflate` 不要开） |

**坑**：HTTP 层返回 `101 Switching Protocols` 是 nginx 给的，**不代表应用层接受了会话**。未绑定设备发完 `hello` 后会被立刻 Close。判断成功的唯一标准是**收到服务端的 `hello` JSON**。

### 客户端 hello

```json
{
  "type": "hello",
  "version": 1,
  "features": { "mcp": true },
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

发出后**等待服务端 `hello`，超时 10 秒**。收到才算连接成功。

### 服务端 hello

```json
{
  "type": "hello",
  "transport": "websocket",
  "session_id": "xxx",
  "audio_params": { "format": "opus", "sample_rate": 24000, "channels": 1, "frame_duration": 60 }
}
```

必须校验 `transport == "websocket"`，并把 `session_id` 存起来 —— 后续所有消息都要带。

## 七、消息全表

### 客户端 → 服务端

| 消息 | 构造 |
|---|---|
| 开始监听 | `{"session_id":"","type":"listen","state":"start","mode":"auto"}` |
| 停止监听 | `{"session_id":"","type":"listen","state":"stop"}` |
| 唤醒词上报 | `{"session_id":"","type":"listen","state":"detect","text":"小智"}` |
| 中止 | `{"session_id":"","type":"abort"}` 或带 `{"reason":"wake_word_detected"}` |
| MCP | `{"session_id":"","type":"mcp","payload":{...JSON-RPC 2.0...}}` |

`mode` 映射：`REALTIME→realtime`、`AUTO_STOP→auto`、`MANUAL→manual`。

`abort` 的 `reason` 字段**只在唤醒词中止时加**，用户打断时 `py-xiaozhi` 不发 reason。

### 服务端 → 客户端

| type | 字段 | 处理 |
|---|---|---|
| `hello` | `transport`、`session_id`、`audio_params` | 存 session_id，标记通道打开 |
| `stt` | `text` | 显示用户说的话 |
| `llm` | `emotion`、`text` | 更新表情 |
| `tts` | `state`: `start` / `stop` / `sentence_start` | 见下 |
| `mcp` | `payload`（JSON-RPC 2.0） | 执行工具调用并回执 |
| `system` | `command`（如 `reboot`） | 系统级指令 |
| `alert` | `status`、`message`、`emotion` | 弹警告 |
| `custom` | `payload` | 可选，需服务端开启 |
| 二进制帧 | Opus 音频 | 解码播放 |

`tts.state == "sentence_start"` 时带 `text` 字段，用于显示字幕。

**重要**：设备处于 `LISTENING` 状态时收到的二进制帧要**丢弃**，否则会和麦克风流打架。

### 已废弃

`type: "iot"` 已废弃，全部走 `type: "mcp"`。

## 八、音频管线

### 编码

`opuslib.Encoder(16000, 1, APPLICATION_VOIP)`，用 `encode_float`（float32 PCM 输入）。

安卓对应：

```
AudioRecord(MediaRecorder.AudioSource.VOICE_COMMUNICATION,
            16000, CHANNEL_IN_MONO, ENCODING_PCM_FLOAT, bufferSize)
```

用 `VOICE_COMMUNICATION` 音源会自动挂上系统 AEC/NS。

### 解码

`opuslib.Decoder(24000, 1)`，`decode_float(opusData, frameSize, decode_fec=False)`。

输出用 `AudioTrack`，采样率按服务端 hello 返回的 `sample_rate`（通常 24000）。

### 上下行必须隔离

上行 16 kHz、下行 24 kHz 是**两个独立的采样率**，不要共用一个编码器实例。

### Opus 帧大小计算

```
输入帧样本数 = 16000 × frameDuration / 1000     // 20ms→320, 60ms→960
输出帧样本数 = 24000 × frameDuration / 1000     // 20ms→480, 60ms→1440
```

### 回声消除

- 优先用 `VOICE_COMMUNICATION` 音源 + 系统 `AcousticEchoCanceler`
- 效果因机型差异大，这是最难调的一块
- 备选：WebRTC 的 APM（`py-xiaozhi` 用的是 `libs/webrtc_apm`），安卓上可引入 `org.webrtc` 的 APM 模块

### 打断

`SPEAKING` 状态下检测到用户说话（能量/VAD）→ 发 `abort` → 状态切 `LISTENING` → 清空播放缓冲。

## 九、状态机

三态：`IDLE` / `LISTENING` / `SPEAKING`。

采集音频的条件（`py-xiaozhi` 的 `should_capture_audio()`）：

```kotlin
fun shouldCaptureAudio(): Boolean {
    if (deviceState == LISTENING && !aborted) return true
    return deviceState == SPEAKING && aecEnabled && keepListening && listeningMode == REALTIME
}
```

即：监听态采集；**开启 AEC 且在实时模式下，说话时也继续采集**（这是实现"说话可被随时打断"的关键）。

进入 `LISTENING` 时要重置 `aborted` 标志。

## 十、MCP

走 `type: "mcp"`，`payload` 是标准 JSON-RPC 2.0。

服务端下发调用：

```json
{
  "session_id": "xxx",
  "type": "mcp",
  "payload": {
    "jsonrpc": "2.0",
    "method": "tools/call",
    "params": { "name": "self.light.set_rgb", "arguments": {"r":255,"g":0,"b":0} },
    "id": 1
  }
}
```

客户端回执：

```json
{
  "session_id": "xxx",
  "type": "mcp",
  "payload": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": { "content": [{"type":"text","text":"true"}], "isError": false }
  }
}
```

`id` 必须原样回传，否则服务端对不上账。

## 十一、安卓端特有的坑

| 问题 | 解法 |
|---|---|
| 后台被杀 | 前台服务 + `FOREGROUND_SERVICE_MICROPHONE`（Android 14+ 必须声明具体类型），并引导用户关闭电池优化 |
| 麦克风权限 | `RECORD_AUDIO` 动态申请；Android 13+ 还需 `POST_NOTIFICATIONS` 才能显示前台服务通知 |
| 真实 MAC 拿不到 | 自造伪 MAC 并持久化，服务端不校验 |
| AudioTrack 卡顿 | 用 `MODE_STREAM` + 足够大的缓冲，播放前先 `play()` 再写，避免 underrun |
| Opus 库 | 用 NDK 编 libopus（见骨架工程）；纯 Java 的 concentus 性能不足 |
| 省电策略 | 部分厂商（小米/华为）需手动加白名单，否则锁屏即断 |
| 蓝牙耳机 | 采样率协商可能失败，需监听 `AudioDeviceCallback` 做重配 |

## 十二、联调自检清单

按顺序确认：

- [ ] OTA 返回 200（若 400，先查 User-Agent 格式）
- [ ] 响应中 `websocket.url` 与 `token` 已正确提取（token 缺失要兜底 `test-token`）
- [ ] 响应中**没有** `activation` 段（有则需先完成激活）
- [ ] `mqtt.client_id` 不以 `GID_test` 开头
- [ ] `mqtt.subscribe_topic` 不等于 `"null"`
- [ ] `websocket.token` 不等于 `"test-token"`
- [ ] WebSocket 收到服务端 `hello`（不是只看 HTTP 101）
- [ ] `session_id` 已保存并在后续消息中携带
- [ ] 发 `listen/start` 后上行 Opus 帧，服务端能回 `stt`
- [ ] 服务端下发的二进制帧能解码出可听的音频
- [ ] 打断流程：说话时打断，服务端能响应 `abort`

前三步未通过时，后面全部免谈 —— 卡在测试组是唯一的高频失败原因。

## 十三、风险提示

1. **官方从未公开承诺支持第三方客户端**。当前放行是协议开放的自然结果，服务端已在强校验 UA 格式，随时可能加其他校验。
2. 商业产品依赖官方免费额度存在被限流风险。
3. 稳妥替代：自建服务端
   - Python：`xinnan-tech/xiaozhi-esp32-server`（最活跃）
   - Java：`joey-zhou/xiaozhi-esp32-server-java`
   - Go：`AnimeAIChat/xiaozhi-server-go`
